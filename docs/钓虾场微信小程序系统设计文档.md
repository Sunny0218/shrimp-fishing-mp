# 钓虾场微信小程序系统设计文档

## 1. 项目定位

本项目用于钓虾场线上预约、现场开单、微信支付、到店核销、计时结账和基础经营管理。第一版优先使用 `uniapp + unibest` 开发微信小程序，后端能力优先采用微信小程序云开发，减少独立服务器、数据库、域名和运维成本。

系统需要同时支持两类经营方式：

| 类型 | 说明 | 示例 |
| --- | --- | --- |
| 套餐预约 | 用户提前选择固定套餐并支付 | 2 小时套餐 88 元 |
| 实时计费 | 用户随机到店或由员工现场开单，按杆数、时长、阶梯价格结账 | 2 根杆，第一小时 50 元/杆，第二小时 45 元/杆 |

## 2. 第一版目标

第一版目标是跑通完整经营闭环：

| 环节 | 目标 |
| --- | --- |
| 用户登录 | 通过微信身份建立用户档案 |
| 用户预约 | 选择日期、时间段、套餐或实时计费方式 |
| 用户支付 | 通过微信支付完成预付或订单支付 |
| 到店核销 | 服务员扫码或输入核销码确认到店 |
| 开始计时 | 套餐订单或实时计费订单进入进行中 |
| 加时消费 | 支持追加时长和现场商品消费 |
| 结束结账 | 统一计算最终金额并完成订单 |
| 管理配置 | 管理套餐、场次、计费规则、员工权限 |

为了降低首期开发风险，可以先跑通线下收款登记闭环，再接入微信支付。订单和支付字段仍按微信支付闭环预留，避免后续返工。

## 8. 订单状态流转

订单状态统一枚举，避免页面和云函数里散落字符串。

| 状态 | 说明 |
| --- | --- |
| `pending_payment` | 待支付 |
| `paid` | 已支付，等待到店 |
| `checked_in` | 已核销 |
| `in_progress` | 进行中 |
| `pending_checkout` | 待结账 |
| `completed` | 已完成 |
| `cancelled` | 已取消 |
| `refund_pending` | 退款中 |
| `refunded` | 已退款 |

推荐流转：

| 订单类型 | 状态流转 |
| --- | --- |
| 套餐预约 | `pending_payment` -> `paid` -> `checked_in` -> `in_progress` -> `pending_checkout` -> `completed` |
| 实时计费 | `checked_in` -> `in_progress` -> `pending_checkout` -> `completed` |
| 用户取消 | `pending_payment/paid` -> `cancelled` |
| 退款 | `paid/cancelled` -> `refund_pending` -> `refunded` |

如果第一版先不接微信支付，套餐预约可临时使用 `paid` 表示已预约待到店，待微信支付接入后再恢复为 `pending_payment -> paid`。

## 9. 计费设计

### 9.1 套餐订单

套餐订单在创建订单时读取当前套餐价格，并把套餐信息写入订单快照。

这样后续管理员修改套餐价格，不会影响历史订单。

```ts
interface PackageSnapshot {
  packageId: string
  name: string
  durationMinutes: number
  price: number
  rodCount: number
}
```

### 9.2 实时计费订单

实时计费订单根据杆数、开始时间、结束时间、阶梯价格计算。

例子：

| 小时 | 单杆价格 |
| --- | --- |
| 第 1 小时 | 50 元 |
| 第 2 小时 | 45 元 |
| 第 3 小时起 | 40 元 |

如果用户开 2 根杆，钓了 2 小时，则基础费用为：

```text
(50 + 45) * 2 = 190 元
```

计费规则也要写入订单快照。

```ts
interface PricingRuleSnapshot {
  pricingRuleId: string
  name: string
  billingUnit: 'rod'
  minDurationMinutes: number
  roundingRule: 'ceil_hour' | 'ceil_half_hour' | 'grace_minutes'
  graceMinutes?: number
  tiers: PricingTier[]
}
```

### 9.3 金额计算原则

| 原则 | 说明 |
| --- | --- |
| 最终金额以云函数为准 | 前端只展示云函数返回结果 |

## 18. 现场开单计时同步方案

第一版不做实时计费订单押金。服务员现场开单后，顾客是否能同步看到计时信息，取决于订单是否绑定到顾客身份。

### 18.1 推荐流程

1. 顾客先完成微信登录，系统生成 `users` 记录。
2. 服务员现场开单时，通过扫码、搜索手机号或选择顾客，把现场订单绑定到顾客的 `userId` 和 `openid`。
3. 云函数创建 `metered` 实时计费订单，写入 `startedAt`、`rodCount`、`pricingSnapshot` 和 `status: in_progress`。
4. 顾客打开“我的订单”或“订单详情”时，通过 `getMyOrders` / `getOrderDetail` 查询到这笔进行中订单。
5. 页面根据云函数返回的 `serverTime`、订单 `startedAt` 和计费规则展示已用时、当前预估金额。
6. 服务员结账时调用 `previewCheckout` / `checkoutOrder`，最终金额以云函数计算结果为准。

### 18.2 顾客侧展示

顾客订单详情页建议展示：

| 信息 | 说明 |
| --- | --- |
| 开始时间 | 使用订单 `startedAt` |
| 已用时 | 用 `serverTime - startedAt` 计算，页面本地每分钟刷新展示 |
| 杆数 | 使用订单 `rodCount` |
| 计费规则 | 使用订单 `pricingSnapshot` |
| 当前预估金额 | 页面可展示云函数返回的预估值，或定时调用 `getOrderDetail` 刷新 |
| 最终金额 | 结账后展示 `finalAmount` |

### 18.3 数据一致性原则

| 原则 | 说明 |
| --- | --- |
| 最终计时以云端为准 | 开始、结束、结账时间都由云函数写入 |
| 前端只做展示 | 顾客端可以本地滚动显示已用时，但不决定最终价格 |
| 订单必须绑定顾客 | 未绑定顾客的现场订单，顾客无法在“我的订单”中看到 |
| 支持后绑定 | 如果现场先开匿名单，后续可由服务员补绑顾客 openid 或手机号 |
